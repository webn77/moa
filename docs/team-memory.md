# 🧠 팀의 기억 — 지난 대화·결정·자료를 찾아 준다 (PA-73 설계)

## 정해진 것 (2026-09-21 사장님)

> 이슈만 관리하는 게 아니고 **이전 대화 내용·이전 의사결정** 이런 거 다 찾아주는 게 좋다 —
> **이슈와 팀 기억 팀 자료 전부.** 그걸 물어보면 거기에 **관련된 것들로 최신 데이터 위주로** 이야기해 주고.
>
> **이 봇은 프로젝트 관리 봇이고 이슈는 그중 하나다.**

`project.md` 의 다섯째 할 일 **「찾음」** 이 이것이다. 「남김」(적어 두기)과 다른 일이다.

## 한 줄 결론

**지금은 아무것도 새로 만들지 않는다.** 우리 자료 전부가 8만 토큰이라 **다 읽는 것이 가장 정확하다.**
없는 것은 저장소가 아니라 **① 이슈 밖의 논의를 남기는 자리** 와 **② 최신순으로 보여 주기** 둘뿐이다.

## 1. 먼저 쟀다 — 이 숫자가 설계를 정한다

2026-09-21 실측:

| | 토큰(한글 기준) |
| --- | --- |
| 이슈 본문 (제목 + 정의) | 14,831 |
| 이슈별 기록 (`edits`) | 19,606 |
| 문서 전부 (`issues/` 71개 · `docs/` · `research/` · `HISTORY.md` · 회의록 · daily) | **81,922** |
| **Claude 가 한 번에 읽는 양** | **200,000** |

**우리 자료는 한 번에 다 들어간다.** `PA-72` 가 이슈만 보고 내린 결론(「4,672 토큰이라 전부 넣는 게
가장 정확하다」)이 레포 전체에도 그대로 성립한다.

## 2. 그래서 벡터DB·그래프·인덱싱을 지금 만들지 않는다

세 가지 다 **「프롬프트에 다 못 넣는다」 를 푸는 도구**다. 우리는 그 문제가 아직 없다.

| 도구 | 언제 필요한가 | 우리는 |
| --- | --- | --- |
| 벡터DB | 너무 커서 다 못 넣을 때 | 8만 < 20만 — 아직 |
| 그래프(GraphRAG) | 여러 다리를 건너야 답이 나올 때 | 이슈↔결정 관계는 `after`·`edits` 로 이미 있다 |
| 자동 인덱싱 | 자료가 계속 불어날 때 | 통째로 읽는 것에 인덱스를 붙일 이유가 없다 |

연구도 같은 말을 한다 — **작은 자료에서는 벡터 검색이 그래프와 비기거나 이기고**, 그래프를 만드는
비용(LLM 으로 관계를 뽑는 것)이 정당화되지 않으며 **오히려 엉뚱한 것을 끌어와 방해가 된다**
([arXiv 2506.05690](https://arxiv.org/pdf/2506.05690) · [VentureBeat](https://venturebeat.com/orchestration/stop-graphing-everything-when-graphrag-actually-beats-vector-rag)).

**만들지 않는 것도 설계다.** 지금 만들면 8만 토큰을 쪼개 넣느라 **덜 정확해진다** — `PA-68` 이 그
증거다 (AI 에게 다른 이슈를 안 보여 줘서 선행을 못 찾았다).

## 3. 어디서 무엇을 찾나 — 두 곳이면 된다

```
과거 대화        → Slack 검색 (낱말)         PA-65
과거 결정·이슈   → 우리 GitHub (전부 읽기)    이미 있다
```

**Slack 검색은 낱말 검색이다.** 뜻으로 찾지 않는다:

| 물음 | Slack 검색 |
| --- | --- |
| 「맥미니 얘기 언제 했지?」 | ✅ 낱말이 있다 |
| 「서버 비용 얘기」 | ✅ |
| 「그때 왜 그렇게 정했죠?」 | ❌ 낱말이 없다 |

**빈칸은 우리 기록이 메운다.** 뜻으로 찾아야 하는 것(결정·이슈 정의·체크리스트·`edits`)은 Slack 이
아니라 GitHub 에 있고, 다 읽으므로 낱말이 달라도 AI 가 알아본다. **그래서 벡터가 없어도 된다.**

### Ringo 는 다르게 한다 (2026-09-21 바로잡음)

Ringo 본인의 답: 「Slack 메시지 원본 → Slack 서버 · **메모리·요약 → Ringo 서버**」.
**자기 서버에 복사해 갖고 있다.** 우리가 Slack 검색을 쓰는 이유는 Ringo 를 따라서가 아니라
**원본이 이미 Slack 에 있어 복사할 이유가 없기 때문**이다 (`PA-65` 의 옛 「왜」 가 틀렸었다).

그리고 **Ringo 도 초대된 채널만 본다** — 저장 방식과 무관하게 Slack 이 원래 그렇다.

## 4. 없는 것 둘 — 이것만 만든다

### ① 이슈 밖의 논의를 남기는 자리

오늘 하루 나눈 것(맥미니·서버 비교·**왜 `update` 를 안 만들기로 했는지**)은 Claude 가 손으로
`HISTORY.md` 에 적었기 때문에만 남아 있다. **봇은 하나도 모른다.**

이슈 스레드 안의 이야기는 `edits` 로 남는다. **밖에서 정해진 것**이 샌다 — 그 자리가 필요하다.
`PA-22`(결정 기록 → `decisions/`) 가 이미 그 카드다.

### ② 최신 것을 먼저

**재료는 이미 다 있다** — `card_ts` · `edits[].date` · `finished` · `timeline()`.
8만 토큰짜리 자료에서 「최신 위주」 는 **검색이 아니라 정렬**이다.

자료가 커지면 연구에서 쓰는 방식이 있다 — **관련도 × 시간 감쇠**(반감기 14일쯤)를 섞은 점수
([arXiv 2509.19376](https://arxiv.org/pdf/2509.19376)). **그때 붙인다.**

## 5. 언제 이 설계가 깨지나 — 선을 미리 긋는다

| 신호 | 그때 무엇을 |
| --- | --- |
| **자료가 15만 토큰을 넘음** | 골라 넣기 시작 — 먼저 열린 이슈·최근 90일로 좁힌다 |
| **Notion·Drive 를 붙임** (`PA-72`) | 문서 300개면 수십만 토큰 — **여기서 벡터가 필요해진다** |
| **Slack 대화 전체를 넣기로 함** | 아직 **안 쟀다** — `PA-65` 가 있어야 잰다 |
| 답이 느려지거나 비싸짐 | 자주 쓰는 것만 추려 캐시 |

**지금 모르는 숫자는 하나 — Slack 대화 전체의 크기다.** `PA-65` 를 할 때 먼저 잰다.

## 6. 순서

| | 무엇 | 왜 이 순서인가 |
| --- | --- | --- |
| 1 | **`PA-22` 결정 기록** | 남길 자리가 없으면 꺼낼 것도 없다 |
| 2 | **`PA-64` 과거 맥락 묻기** | 우리 기록(8만 토큰)만으로 먼저 답해 본다 — **새로 만들 것이 없다** |
| 3 | **`PA-65` Slack 검색** | 우리 기록으로 못 찾는 것이 실제로 무엇인지 보고 나서 붙인다 |
| 4 | **`PA-23` 이슈 히스토리** | 정본 md 를 두껍게 |
| 5 | **`PA-72` 밖의 문서** | 여기서 벡터를 다시 검토한다 |

**2번을 먼저 하는 것이 이 설계의 핵심이다** — 도구를 만들기 전에 **지금 있는 것으로 얼마나 되는지**
본다. 안 해 보고 벡터부터 만들면 필요 없는 것을 만든다.

**이 순서는 카드의 `after` 에도 넣었다** (`PA-73` → 22 → 64 → 65 → 23 → 72). 문서에만 적고
카드에 안 넣으면 봇은 다섯을 **한꺼번에 「할 수 있다」** 고 보고, 점수 순으로 아무거나 먼저
내민다 — 결정이 문서에는 있고 데이터에는 없는 상태다. `PA-74` 가 그렇게 생긴 문제다.

`PA-73` 자신은 **설계가 끝나면 할 일이 없다.** 체크리스트(「근거와 함께 답한다」·「최신 것을 먼저」)은
자식들이 채우므로, **닫히는 것은 `PA-22`·`PA-64` 가 끝난 뒤**다.

## 7. 정해야 할 것 (만들면서)

- **어디까지 보나** — `PA-65` 의 유저 토큰은 **개인 DM 까지** 본다. 팀 채널만? 봇이 초대된 곳만?
- **답에 출처를 어떻게 붙이나** — 「언제·어디서 나온 이야기인지」 없이는 믿을 수 없다
- **안 물어도 꺼내나** — 지금은 **물을 때만**. 먼저 꺼내는 것은 `PA-17`(아침 알림) 쪽 일이다
