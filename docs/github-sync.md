# 이슈 검증 + GitHub 동기화 규칙 (설계)

정한 사람: 이동원 (2026-09-20). 지금은 내보내는 시점이 코드 8곳에 흩어져 있어서, 정의가 있는데 GitHub 에 없는 카드가 21건 생겼다.

## 1. 어디에 무엇이 있나
| 곳 | 무엇 | 누가 쓰나 |
| --- | --- | --- |
| `cards.json` | 실행 상태 전부 (담당·목표일·체크·기록) | 봇 |
| `issues/NNN-….md` | 이슈 정본 — 정의 · 체크리스트 · 날짜별 기록 · 산출물 | 봇이 쓰고 사람이 읽는다 |
| GitHub Issue | 위 md 의 거울 | 밖에서 보거나 이어받을 때 |
| Slack 카드 | 보는 면 | 팀 |

## 2. GitHub 에 올리는 시점 — 「번호가 생기면 올린다」
- **번호 = 사람이 하기로 정한 일**이다. #51 분류함이 들어가면 요청은 번호 없이 분류함에 있다가, 사람이 [백로그에 올리기] 를 눌러야 번호를 받는다
- 규칙이 한 줄이라 예외를 기억할 필요가 없다 — **번호가 있으면 GitHub 에도 있다**
- 「진행 중일 때 올린다」 는 안 쓴다: 백로그가 GitHub 에서 빠져 목록이 두 곳으로 갈리고, 사람도 AI 도 「진행 중」 을 정확히 눌러 주지 않는다

| 언제 | GitHub |
| --- | --- |
| 번호가 생김 | 이슈 생성 (검증 통과한 것만) |
| 제목 · 정의 · 체크리스트 · 상태 · 담당이 **실제로** 바뀜 | 같은 이슈 갱신 |
| 완료 · 취소 | 닫음 (사유 포함) |
| 담당이 풀림 | 그대로 둔다 |

## 2-1. 번호는 하나다 — gh#N = 카드 #N (2026-09-20 추가, 사용자 제기)
Slack 카드 번호와 GitHub 이슈 번호가 다르면 말할 때마다 「우리 58번이 깃헙 6번」 을 붙여야 한다.

**번호의 주인은 GitHub 이다** (#60, 2026-09-20). 카드를 만들 때 **GitHub 이슈를 먼저 만들고 그 번호를 쓴다**.

- PR 이 번호를 먹어도, 밖에서 이슈를 만들어도 **어긋날 일이 없다** — 따라가는 게 아니라 받아 오기 때문이다
- 밖에서 만든 이슈는 번호가 이미 맞으므로 **카드만 붙이면 된다** (`import_github`, 2분마다 · 한 번에 5건)
- 우리가 만든 이슈(제목이 `#N …`)와 자리표시(`(빈 번호)`)는 가져오지 않는다. 한 번 가져온 번호도 다시 안 가져온다
- **번호를 못 받으면 카드를 만들지 않는다.** 로컬 번호로 넘어가면 다음에 받아 온 번호와 겹친다 —
  그게 2026-09-20 에 59개를 손으로 맞추게 한 원인이다
- **번호는 내용이 갖춰진 뒤에 나간다** (2026-09-20 저녁 결정). `🎫 한 줄` 은 먼저 **정리안**이 되고,
  사람이 👍 를 눌러야 GitHub 이슈·번호·카드가 생긴다. 정리안이 미정투성이(5칸 중 3칸 이상)면
  만들기 단추를 주지 않고 한 줄 더 묻는다 — **부실한 이슈는 GitHub 에 아예 안 생긴다**
- **앞말은 레포를 가리킨다 — 프로젝트가 아니다** (2026-09-20 결정, `research/benchmark.md` 결론).
  `PA-40` 의 `PA` 는 **번호를 준 레포**의 약칭이고, 프로젝트는 앞말이 아니라 **카드의 한 칸**이다.
  프로젝트가 레포를 가로지를 수 있어야 하기 때문이다 — 붙여 버리면 한 프로젝트를 레포 둘로 쪼개는 날
  `PA-40` 이 두 개가 된다. 앞말은 **보이는 표시일 뿐** 저장·짝짓기·파일 이름에 쓰지 않는다
- **sub-issue 도 같은 번호 공간이다** (2026-09-20 실측). 부모에 붙여도 번호가 안 바뀌고 `parent_issue_url` 만 생긴다 —
  곧 sub-issue 는 별도 번호가 아니라 **그냥 같은 레포의 이슈**다
- GitHub 을 안 쓰는 팀은 예전처럼 봇 안의 카운터(`STATE.next`)를 쓴다
- 앞선 방식(카운터가 정하고 GitHub 이 따라옴 + `pad` 로 빈 번호 메우기)은 **버렸다**. 한 번 맞추는 데 쓴
  `renumber_github.py` 도 지웠다 — 다시 어긋나지 않으므로 필요 없다

## 3. 트래픽 — 시점이 아니라 이 둘로 줄인다
1. **바뀐 것만 보낸다.** 제목·본문·상태를 지문으로 비교해서 같으면 GitHub 을 부르지 않는다 (지금은 상태를 누를 때마다 무조건 보낸다)
2. **파일 커밋은 모아서.** 바뀐 파일이 생기면 5분 창을 열고, 창이 닫힐 때 한 번에 커밋·푸시한다.
   바뀐 게 없으면 아무 일도 하지 않는다(주기적으로 도는 것이 아니다). 봇을 끌 때 남은 것은 마치고 꺼진다
- GitHub 이슈 자체는 **모으지 않는다.** 사람이 보는 곳이라 늦으면 안 된다. API 한도(시간당 5,000)에 비해 우리 양은 하루 수십 번이라 문제가 되지 않는다

## 4. 검증 — 세 지점 (모두플로2 방식)
「모자란 것은 막지 않는다. 화면을 거짓말하게 만드는 것만 막는다」 · 「모르는 값은 통과가 아니라 걸린다」

**2026-09-20 정정: 「막는 것」 도 내보내기를 막지 않는다.** #60 부터 번호를 받을 때 이슈가 먼저 생기므로,
여기서 멈추면 GitHub 이 옛 상태로 남는다 — 실제로 취소한 #63 이 GitHub 에서 열린 채로 있었다.
아래 「막는 것」 은 이제 **스레드에 한 번 알리는 것**이고, 같은 말은 되풀이하지 않는다.

| 언제 | 꼭 채워야 하는 것 (스레드에 알림) | 알려주는 것 (스레드에 한 줄) |
| --- | --- | --- |
| 번호를 받을 때 | 제목 없음 · 이슈 정의 비어 있음 · 체크리스트 0개 · 번호 중복 · 없는 선행 번호를 기다림 | 목표일 없음 · 로드맵 단계 없음 · 기능 없음 |
| 진행 중으로 갈 때 | (없음) | 체크리스트 0개 — 「끝났다고 볼 조건을 한두 줄 알려 주세요」 |
| 완료로 갈 때 | (없음 — 사람이 확인) | 체크리스트 2/5만 체크됨 · 산출물·커밋이 하나도 없음 · 목표일보다 N일 늦음 |

완료는 **막지 않는다.** 팀이 쓰는 곳이라 막으면 일이 멈춘다. 대신 확인하는 사람에게 빠진 것을 그 자리에서 보여 준다.

## 5. 만드는 순서
1. 검증을 순수 계산으로 `core.py` 에 (테스트로 고정) — 모두플로2의 `checks.py` 방식만 가져온다. 상태 모델은 우리 것 그대로
2. 내보내는 자리를 `flows/github.py` 한곳으로 모으고, 위 시점 규칙만 남긴다
3. 커밋 모으기(5분 창) · 지문 비교
4. 밀린 이슈 올리기 — 지금 정의가 있는 21건
5. (다음 이슈) 정본을 md 로 옮기고 `cards.json` 은 다시 만들 수 있는 캐시로 — 그때 모두플로2의 `validate` 를 거의 그대로 쓸 수 있다

## 6. 누가 올렸나 — 셋을 다르게 (2026-09-21 사장님 요청)

봇이 켤 때 「지금 어떤 버전인지 누가 올렸는지」 를 Slack 에 알린다 (`gh_link.version_line`).
그러려면 **셋이 서로 다른 git 이름으로 올려야** 한다.

| 올리는 이 | git 이름 | 어떻게 |
| --- | --- | --- |
| 봇 | `moa-bot` | `gh_link.commit()` 이 `-c user.name=` 으로 박아 둠 |
| Claude | `Claude` | 커밋할 때 **`--author="Claude <noreply@anthropic.com>"`** 를 붙인다 |
| 이동원 | 맥의 git 이름 | 그대로 |

**Claude 가 `--author` 를 빠뜨리면 사장님 계정으로 찍혀 둘이 한 사람처럼 보인다.**
그러면 「누가 올렸는지」 칸이 틀린 값을 자신 있게 보여 주게 되므로, 없느니만 못하다.

레포에 `user.name` 을 박지 않는 이유: 사장님이 이 레포에서 직접 커밋할 때도 그 이름이 된다.
