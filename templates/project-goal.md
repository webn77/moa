# 프로젝트 목표 틀

새 프로젝트를 시작할 때 이 순서로 채운다. 위에서 아래로 한 줄씩 이어져야 한다.
짝이 안 맞는 줄(개선이 없는 할 일, 지표가 없는 할 일, 할 일에 안 붙는 기능)은 빼거나 다시 쓴다.

| 칸 | 묻는 것 | 규칙 |
| --- | --- | --- |
| 0. Pain point | 누가 · 무엇 때문에 · 얼마나 곤란한가 | 3~4줄. 굵은 제목 + 결과. 근거가 있으면 붙인다. 할 일은 여기서 나온다 |
| 0-1. 왜 기존 방법이 아닌가 | 이미 쓰는 도구로는 왜 안 되나 | 비교 표 한 개. 경쟁 도구의 비슷한 기능도 공정하게 적는다 |
| 1. 목표 | 무엇을 이루나 | 한 문장 + 재는 법 (기준값 → 목표값). 기준값이 없으면 어디서 잴지부터 |
| 2. 개선 | 무엇이 나아지나 | 「지금 → 바뀐 뒤」 2~3줄. 사람이 느끼는 불편으로 쓴다 |
| 3. 할 일 (이니셔티브) | 그래서 무엇을 하나 | 개선 하나에 할 일 하나 |
| 4. 기능 (상위 이슈) | 할 일마다 무엇을 만드나 | 할 일마다 2~4개. 이슈는 반드시 기능 하나에 붙는다 |
| 5. 성공 기준 (지표) | 무엇으로 성공을 보나 | 할 일마다 1개. 숫자 + 재는 법. 봇이 셀 수 있으면 봇이 센다 |
| 6. 단계 (로드맵) | 언제까지 어디까지 | 기획 → 프로토타입 → 개발·도그푸딩 → PoC → 판단 → 파일럿 → 본사업. 단계마다 통과 기준 |

```text
Pain point ─ 목표 ─ 개선 ①②③ ─ 할 일 ①②③ ─ 기능(상위 이슈) ─ 이슈
                        └─ 성공 기준 ①②③
단계(시간 축)는 따로 — 이슈마다 단계 하나
```
