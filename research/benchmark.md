# 🔍 벤치마킹 — Slack 안의 AI 프로젝트 비서

조사일 2026-09-19. 비교 기준은 우리가 만든 기능. 확신도는 높음 · 중간 · 낮음으로 표시한다.

## 한 줄 결론
**「Slack 쓰는 팀을 위한 AI 프로젝트 비서」 자리는 비어 있다 — 확신도 중간.** 국내 최근접은 플로우 「리패턴」(자기 협업툴 안에서만 동작).

## 왜 Jira·Linear가 아닌가

| | Jira · Linear | 우리 |
| --- | --- | --- |
| 일하는 곳 | 별도 프로그램 (Slack 연동은 알림·입구 정도) | Slack이 메인 화면, GitHub는 밑단 저장소 |
| 입력 | 사람이 옮겨 적는다 | 대화가 곧 입력, 봇이 모아서 정리 |
| AI | 검색 · 요약 · 분류 (사람이 불러야 움직임) | 비서가 먼저 움직인다 — 나누고 · 알리고 · 기록 |
| 쓰는 사람 | 익숙해야 쓴다 | Slack만 쓸 줄 알면 된다 |
| 비용 | 사람당 월 과금 | 무료 Slack + GitHub |

Linear Asks(Slack 메시지 → 이슈)·Jira Rovo(AI)도 있다. 차이는 「AI가 있냐」가 아니라 「Slack이 본거지이고 AI가 비서로 먼저 움직이냐」.

## Ringo — 같은 워크스페이스에 붙여 놓고 직접 물어봤다 (2026-09-21)

가장 가까이 있는 제품인데 표에 없었다. 사장님과 같이 DM 으로 세 가지를 물어 확인했다.

| | Ringo | 우리 |
| --- | --- | --- |
| 자기 소개 | 「**팀의 기억**을 챙기는 AI 동료」 | 「Slack 안의 AI **프로젝트 비서**」 |
| 이슈를 만드나 | **만든다** — 다만 Jira·Linear 에 **얹힌다**. 연결이 없으면 자기 「Ringo 투두」 | GitHub 이슈가 **정본** |
| 전제 | **이미 트래커를 쓰는 팀** | **트래커가 없는 팀** (Jira 없이 Slack 하나로) |
| 담당자 | 사람에게 **되묻는다** | AI 가 추천 → 사람이 확정 (역할·여유를 보고) |
| 순서·과부하·마감 | 안 한다 — **Jira 가 하니까** | 우리가 한다 (P1~P4 · 동시 작업 제한 · 선행) |
| 보는 범위 | **초대된 채널만** | 초대된 채널 + 프로젝트 방 |
| **어디에 저장하나** | **Ringo 서버**(클라우드) — 메모리·요약·투두 전부. 워크스페이스별 격리 | **팀의 GitHub 레포** — 이슈·md·기록 |

**저장 위치가 가장 큰 차이다.** Ringo 본인의 답:

> Slack 메시지 원본 → Slack 서버 · Ringo 메모리·요약 → **Ringo 서버** · Ringo 투두 → **Ringo 서버**

우리는 남의 서버를 거치지 않는다 (`docs/install.md` 「왜 원클릭이 아닌가」). 대신 팀이
토큰을 직접 만들고 자기 레포에 쌓는다 — **봇을 꺼도 이슈와 md 가 그대로 남는다.**

### 언제 나왔나 · 어디에 사는가 (2026-09-21 확인)

**이번 주에 나왔다.** Product Hunt 에 「Launched this week」, 만든 곳 `@ringoai`,
소개가 **「Seamless AX Co-worker」** — 우리가 쓰는 **AX** 와 같은 말이다. GPT-6 Astra 기반이라고 밝힌다.
**우리와 거의 동시에 시작한 제품**이라 「워크스페이스 대화를 읽으며 따라잡는 중」 이라고 인사한다.

**앱 홈은 안내판이다** — 이슈 목록도 진행률도 누가 뭘 맡는지도 없다:

> Ringo 에 오신 걸 환영해요! · 워크스페이스 정보(프로젝트·에이전트) ·
> 시작하기(DM · 멘션 · **데일리 브리핑**) · 설정(**채널 및 소스** — 학습 범위 · 언어·모델·멤버·결제)

**캔버스 탭이 아예 없다.** 우리가 작업판으로 쓰는 기능을 쓰지 않는다.

| | Ringo | 우리 |
| --- | --- | --- |
| 본거지 | **DM · 멘션** | 프로젝트 방 카드 + 앱 홈 + 캔버스 |
| 앱 홈 | 안내·설정 | **현황판** (오늘·프로젝트·내 일·가져갈 수 있는 일) |
| 이슈 보는 곳 | 「이슈 링크」 로 **Slack 밖으로** | 카드·상세·홈 전부 Slack 안 |
| 캔버스 | 없음 | 작업판 |

### 우리가 Ringo 보다 **부족한 것** (2026-09-21)

남들에게 없는 것만 적어 두면 문서가 우리를 속인다. 못 하는 것도 적는다.

| | 부족한 것 | 지금 |
| --- | --- | --- |
| 1 | **대화 전체를 안 읽는다** | Ringo 는 고른 채널을 통째로 학습. 우리는 **이슈 스레드만** (#64·#65 — 다만 Ringo 도 초대된 채널만 본다) |
| 2 | **데일리 브리핑** | Ringo 는 있다. 우리 **#17 은 아직 안 함** (아침 현황은 #59 로 채널에 한 번 올린다) |
| 3 | **아무거나 물어볼 수 있는 대화** | 정해진 갈래(목록·현황·정리·순서)뿐이다. **「하이」 에 「하이로 찾은 이슈 없어요」 라고 답했다** (2026-09-20) |
| 4 | **설정을 화면에서** | Ringo 는 학습 범위·언어·모델을 UI 로. 우리는 `config.json` 을 손으로 |

**3 이 제일 아프다.** 못 알아들은 말을 검색으로 떨어뜨리면 **봇이 바보처럼 보인다** —
「무엇을 할 수 있는지」 로 답해야 한다.

### 채널에서 부르면 — 묻지 않고 **바로 만든다** (2026-09-21 실측)

`#프로젝트` 에서 `@Ringo 로그인이 자주 끊겨요. 30분쯤 쓰면 … 이거 이슈로 정리해 줄래?` 라고 했더니:

> **이슈로 등록했습니다**
> 로그인 세션 만료 이슈 — 약 30분 사용 시 재로그인 요구됨 (**우선순위: 높음**)
> 증상 — … · 확인 필요 사항 — 세션 타임아웃 설정값, 리프레시 토큰 로직, …
> 이슈 링크에서 상세 내용 확인·수정하실 수 있어요.

| | Ringo | 우리 |
| --- | --- | --- |
| 만드는 시점 | **바로** — 만들고 나서 고치라고 한다 | 초안을 보여 주고 **사람이 눌러야** 번호가 난다 |
| 우선순위 | **스스로 붙인다** (높음) | 점수 계산 → P1 은 사람만 |
| 내용이 모자라면 | 그대로 만든다 | **안 만든다** — 한 줄 더 묻는다 (#57) |
| 답하는 자리 | 채널 멘션 → **스레드** | 같다 |

**어느 쪽이 옳은 게 아니라 값이 다르다.** Ringo 의 이슈는 자기 투두라 틀려도 지우면 그만이다.
우리 이슈는 **GitHub 에 남고 번호를 먹는다** — 그래서 문을 세워 뒀다 (#11 「AI 는 제안까지, 누르는 건 사람」).
다만 **DM 에서는 Ringo 도 담당자를 되물었다** — 자리에 따라 다르게 군다.

**가져온 것**: 기다리는 동안 **문구를 바꿔 보여 주는 것** — 「필요한 정보를 찾는 중」 ·
「관련 내용을 살펴보는 중」 · 「답변을 정리하는 중」. 같은 기다림인데 덜 답답하다.
우리는 한 줄에 시간만 붙이고 있었다 (2026-09-21 `slack.Step.waiting` 에 반영).

다만 **Ringo 의 문구는 순서대로 가지 않고 돌아간다** (정리하는 중 → 살펴보는 중 → 찾는 중).
진짜 진행이 아니라 살아 있다는 표시다. 우리는 순서대로 가고 마지막에서 멈추며 **지난 시간을 함께** 적는다 —
그게 유일하게 진짜인 정보다.

**겹치는 것**: #64 팀 기억 · #65 전체 검색은 Ringo 가 하는 일과 같다. 다만 Ringo 도
**초대된 채널만** 보므로 「대화 전체 기억」 은 어차피 반쪽이다 — 우리는 「이 이슈의 과거」 로
좁히는 쪽이 낫다 (그 기록은 우리가 만든다).

## 이슈 번호와 프로젝트 구분 — Jira · GitHub · Linear (2026-09-20 조사, #66)

| | Jira | GitHub | Linear |
| --- | --- | --- | --- |
| **번호를 주는 단위** | project | **repository** (issue·PR 한 줄로 셈) | **team** (project 아님) |
| 사람이 읽는 키 | `PROJ-123` | `#40` (앞말 없음) | `ENG-123` |
| 앞말을 사람이 정하나 | O | X (레포 이름이 사실상 앞말) | O |
| 나중에 바꿀 수 있나 | **O** — 옛 키가 계속 열린다 | 해당 없음 | O (규칙은 문서 미확인) |
| 프로젝트 간 이동 | O · 옛 키가 **모두 쌓여** 리다이렉트 | O (같은 주인 한정) | O · 새 번호를 준다 |
| 옛 링크 | 열린다. 다만 **글자 표기는 안 바뀐다** | 원 주소가 넘겨준다 | 열린다. **표기는 안 바뀐다** |
| 가로질러 보기 | JQL · 보드 | Projects | Project 가 여러 team 에 걸친다 |
| 화면에서 구분 | 키에 앞말이 들어 있다 | `owner/repo#40` | ID 에 앞말이 들어 있다 |

**우리 설계에 곧장 걸리는 것 다섯**

1. **번호 주는 단위와 묶는 단위는 다르다.** Linear 는 team 으로 번호를 주고 project 로 묶는다(project 가 team 을 가로지른다).
   「레포 하나 = 프로젝트 하나」 는 둘을 붙여 버리는 선택이다 — 나중에 **한 프로젝트를 레포 둘로 쪼갤 수 없다.** 알고 받아들일지 정해야 한다
2. **보이는 키는 바뀌고, 정체는 안 바뀐다.** 셋 다 키를 바꾸거나 다시 주면서 옛 키를 계속 열어 준다.
   안에는 안 바뀌는 id 를 두고, **지나간 키를 전부 쌓아** 둬야 한다 (Jira 가 그렇게 한다)
3. **Slack 에 맨 `#40` 을 그리지 않는다.** Slack 은 원래 여러 프로젝트가 섞이는 화면이다.
   그 프로젝트 방 안에서만 번호만 쓰고, 밖에서는 `PA-40` 또는 `owner/repo#40` 으로 쓴다
4. **앞말을 키로 쓰지 않는다.** 앞말은 바뀌는 표시일 뿐이다 — DB 키·방 짝짓기·파일 이름에 쓰면 이름을 바꿀 때 깨진다
5. **옮기면 번호가 바뀐다고 보고 설계한다.** GitHub 이 번호를 주는 구조라 보존이 불가능하다.
   지키려 하지 말고 **옛→새 짝을 적어 두고 Slack 스레드를 갱신**한다 (셋 다 「표기가 안 바뀐다」 가 실제 불편이다)

**GitHub sub-issue 는 부모 레포 번호를 그대로 먹는다 — 2026-09-20 실측.**
`(빈 번호)` 제목으로 이슈를 하나 만들었더니 레포 다음 번호인 **#67** 이 나왔고, 그대로 #66 의 자식으로 붙였는데
**번호가 바뀌지 않았다.** 대신 `parent_issue_url` 칸이 생긴다 — 부모를 찾는 길은 이것이다.
곧, **sub-issue 는 별도 번호 공간이 아니라 그냥 같은 레포의 이슈**다 (확인 뒤 #67 은 닫음).

**확인 못 한 것** (문서에 없어서 비워 둠): Jira subtask 키 형식 · Jira 프로젝트 키 기본 최대 길이 ·
Linear team 약칭 글자·길이 규칙 · GitHub 이동 시 번호 변경 명문.

## 결론 — 우리가 고른 것 (2026-09-20, 이동원 결정)

**앞말은 레포(번호 공간)를 가리킨다. 프로젝트는 앞말이 아니라 카드의 한 칸이다.**

「프로젝트 하나 = 레포 하나」로 **붙이지 않는다.** 붙이면 한 프로젝트를 레포 둘로 쪼개는 날 `PA-40` 이 두 개가 된다.
번호 공간(레포)보다 묶음(프로젝트)이 **더 굵어질 수 있어야** 하고, Linear 가 team 으로 번호를 주고
project 로 묶는 이유가 정확히 이것이다.

#60 에서 번호의 주인을 GitHub 으로 정한 순간 **번호를 주는 단위는 이미 레포로 고정됐다.**
그래서 이건 「레포냐 Linear 냐」 의 선택이 아니라, **GitHub 위에서 Linear 의 구조를 흉내 내는** 방법이다.

**AI 에게는 맨 `#40` 이 가장 나쁘다.** 어느 프로젝트인지를 방 맥락에서 추론해야 하고, 추론하면 틀린다.
사람은 기억으로 메우지만 AI 는 매번 다시 읽는다 — **맥락 없이 혼자 풀리는 식별자**가 필요하고,
그게 레포 범위 앞말이다.

**번호는 이름이지 구조가 아니다.** 2026-09-20 기준 열린 31건에서 기능 31/31 · 로드맵 단계 29/31 인데
**선행 순서(`after`)는 6/31** 이다. 칸은 이미 있는데 안 채워져 있다 — AI 는 사람보다 이 간선이 더 필요하다
(「이게 저것 때문에 막혀 있다」 를 모르면 「다음에 뭘 하죠」 에 답할 수 없다). 이건 #66 과 **다른 일**로 떼어 놓는다.

## 🔲 할 일 **안**의 체크 목록 — 다른 곳은 뭐라고 부르나 (2026-09-22 조사)

사장님: 「할일들이 task잖어 이거 안에 체크리스트 뭐 해야 하나 이거 말한 거야」 ·

우리에게는 이미 이 칸이 있다 — 이름이 **「완료 조건」** 이라 「뭘 하나」 로 안 읽힐 뿐이다.
71건 중 59건에 들어 있고, 그 안에 **할 거리**(「권한 단계 표 문서화」)와
**통과 조건**(「알림이 1회만 발송된다」)이 섞여 있다.

### 읽은 것 셋

**① 대부분은 목록을 하나만 둔다.** 「완료 기준」 을 따로 가진 곳은 Jira 뿐이고, 그나마
기본 기능이 아니라 **앱이 파는 것**이다. 그 앱들이 광고하는 용도가 정확히 우리가 섞어 쓰는 셋이다
— Definition of Done · Acceptance Criteria · TODO. 업계도 **섞이는 것을 문제로 본다**는 뜻이고,
푸는 방법은 칸을 늘리는 게 아니라 **목록마다 이름을 붙이는** 것이다.

**② 가벼운 건 체크박스, 무거우면 승격.** Linear 도 GitHub 도 「본문 체크박스 → 따로 떼어야 할 만큼
커지면 하위 이슈」 한 길이다. 우리도 이미 있다 — 체크 항목이 커지면 「할 일로 만들어줘」 하면 카드가 된다.

**③ 이름은 겹치는지로 고른다.** 우리 화면에 이미 있는 말:
「할 일」(카드 그 자체) · 「액션 아이템」(회의록이 뽑아 카드가 되는 것, `gh_link.py`) ·
「작업판」·「작업 보드」(캔버스와 보드). 그래서 **할 일 목록 ❌ · 액션 아이템 ❌ · 하위 작업 △**
(「작업」 이 이미 캔버스 쪽 말이다) — 남는 것이 **체크리스트** 다. 사장님이 먼저 쓰신 말이기도 하고,
화면에 이미 네모가 그려져 있어 **보이는 것과 이름이 같다.**

### 결론 — 우리가 고를 것

**「완료 조건」 을 「체크리스트」 로 바꾸고, 안에 적는 말을 할 거리로 통일한다.** 칸을 늘리지 않는다 (①).
GitHub 쪽은 이미 `- [ ]` 로 나가고 있어 진행률이 그대로 뜬다 — 고칠 것이 없다.
